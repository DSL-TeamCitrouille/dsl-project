# LLM Protocol

The LLM bot uses an external Large Language Model (via a Flask backend) to select the best move from a list of legal moves generated by the game engine. The model does not compute move legality, it only chooses from moves that are already valid.

This section documents the full protocol: input context, output schema, repair mechanism, and reproducibility parameters.

---

## Input Context Sent to the LLM

Bafore calling the model, the backend builds a comprehensive prompt that brings together two types of information.
First, it includes a clear natural-language explanation of the rules governing the current match (movement, captures, promotion, victory conditions, direction of play, and whether captures are mandatory).
Second, it embeds a structured representation of the entire game state, including all pieces, their positions, and every legal move generated by the engine.
This combination ensures that the LLM receives everything it needs to select a valid and informed move.

The LLM receives the following information:

### 1. All Legal Moves

Each move is serialized as:

```json
{
  "from": { "row": 1, "col": 1 },
  "to": { "row": 2, "col": 2 },
  "capturedIds": []
}
```
The LLM **must choose one of these moves**. It cannot invent new coordinates.

### 2. Game Configuration
- Board size (e.g., 8×8)
- Direction rule (`diagonal`, `orthogonal`, or `any`)
- Mandatory capture rule (`true`/`false`)
- Current player `ID`
- Capture and promotion rules explained in text

### 3. Full Game State
Including for every piece:
```json
{
  "id": "p0",
  "player": 0,
  "row": 1,
  "col": 1,
  "color": "white",
  "isQueen": false
}
````

### 4. Strategy Guidelines

The prompt includes high-level reasoning instructions:

* Protect pieces first
* Avoid exposing pieces to capture
* Prefer safe advancement
* Consider multi-step threats
* Look for chain captures

### 5. Output Format Instructions

The LLM is told to output:

* Strict JSON
* One line only
* No markdown or explanation text

---

## Output JSON Schema

The model must return exactly one JSON object in one line:

```json
{"piece_id":"p4","target":{"row":3,"col":4},"reasoning":"optional short justification"}
```

### Field meanings

* `piece_id`: ID of the piece to move (e.g., "p4")
* `target.row`: Target row (integer)
* `target.col`: Target column (integer)
* `reasoning`: Optional one-sentence description (ignored by engine)

### Validity Requirements

* Must be valid JSON
* Must correspond to a move in legal_moves
* Must reference an existing piece ID
* Must not contain markdown or comments

If these conditions fail, the backend initiates a repair cycle.

---

## Repair Policy

If the LLM returns invalid JSON or an illegal move:

### Step 1 — Backend Validation

* `json.loads()` parsing
* Check that `piece_id` exists
* Check that `(from → to)` matches a legal move

If validation fails it passes to Step 2.

### Step 2 — Repair Prompt

The backend sends a second prompt containing:

* The original full prompt
* The invalid previous answer
* The entire legal_moves list
* A strict JSON schema reminder
* Instructions to return **one line of valid JSON**

This gives the LLM one more chance to provide a valid move.

### Step 3 — Failure Handling

If the second attempt is also invalid:

* Backend responds with `"success": false`
* The frontend (`LLMBot.ts`) logs the failure
* A fallback move is executed:

  * Prefer first capture move
  * Otherwise take first legal move

The game continues without crashing.

## Reproducibility Parameters

The backend exposes several configurable parameters to control stability and consistency of LLM output.

### Model

Default: ***anthropic/claude-3.5-sonnet***


Other options available through **/api/models**.

### Temperature

```json
"temperature": 0.7
```

* Higher → more creative but more error-prone
* Lower → more deterministic

### Token Usage Tracking

Backend logs:

* `prompt_tokens`
* `completion_tokens`
* Total tokens
* Estimated cost based on model pricing

### Caching

Each unique game state is hashed:

```md
hash = md5(sorted_pieces + sorted_moves + current_player + turn)
```

If the same state appears again:

* LLM is **not** queried
* Cached response is returned instantly

This improves speed, reproducibility, and cost efficiency.

### Seeds

OpenRouter only supports seeds for some models.
If unsupported:

* Reproducibility depends on temperature + model + prompt stability
* Backend logs the entire prompt for debugging and replay purposes
